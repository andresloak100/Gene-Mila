documents in full and the repository files they cite, read-only, and wrote what a reviewer would object to, each
objection with the document lines, the claim, the problem, the repository evidence as `file:line` and a fix. Their 107
raw objections were merged into 85 findings (the merge record is in section 4). A second, adversarial reader then took
each finding, re-read the document lines in context and every cited file, and was told to refute it by default: the
verdict is *confirmed* only when the second reader saw the problem in the files, *partly* when the objection stands but
a detail was misread, *refuted* when the evidence did not hold or the plan's dated notes already say what the finding
asks for; it gave its own severity (*reject*: a venue reviewer would return the paper, or the plan as written makes a
reading invalid, unfair or irreproducible; *major*: must change before the first paid session or before submission;

## Where this leaves the two documents (the reader's own summary)

Nothing stands at *reject* after checking: the one objection the reviewers rated so (F01, the planner's hand-written
idea bank) was confirmed as a real, undisclosed lab-only input but rated *major*, since disclosure plus one matched arm
repairs it. The paper's problem is not a wrong number but a frame that the design cannot carry: it asks "which system
finds the better features" while the lab arms and the package arms differ in the code-writing model, the evaluation
throughput, the idea bank, the exploit engine, the selection rule, the prompt and the sandbox at once (F08), and the
abstract states two things the Methods and the run scripts contradict ("the model fixed to one ridge", F04; "every LLM
arm on one LLM", F05). The plan's problems are mechanical and fixable before the probe: nothing records or pins the
foreign arms' software (F17), the probe's pass rule lives in a comment (F18), a free refusal strands a session and a
stop has no path past it (F37), a network call in account mode has no pre-registered consequence (F20), the lab arms
already dropped a parent column that the package arms cannot drop (F21), the proportionality check misses a whole
class of parent-derived candidates (F23), and the frozen batch names a baseline that does not exist on Adamson (F65).
The second reader's late pass added five more confirmed majors of the same kind: the C2 set was written on 16
October by the session that had just recorded which feature family wins, and nothing says so (F19); the fresh-test
batch is defined over models that no exporter can freeze (F27) and names a scoring path the holder cannot run (F30);
the paper's "38 screen-free unique rows" is 40 by the record it cites (F32); and the probe's `.passed` marker is an
empty file that records nothing about the route it cleared (F40). Section 1 lists every major finding with the fix
it needs; section 2 the minor ones; section 3 what the readers covered.

### F04. Lab arms run an undisclosed exploit engine and model-family search; the paper says the model is fixed

**Where:** PAPER 14-15, 84-90; PLAN 24-26. **Lenses:** fairness, venue. **Second reader (first pass):** confirmed, severity major.

**In a reviewer's words:** The abstract states the model is "fixed to one ridge regression", but the lab arms search over ridge, lasso, elastic net and OLS (the planner's JSON, `genemila/prompts.py:37`) and run an undisclosed no-LLM exploit engine (`genemila/exploit.py`, on by default) that proposed 29% of a DeepSeek-planned run's experiments (`docs/results/scaling.md:16`), 61-95% of the scripted control's, and the selected model of one of the three A1 runs already in Table 1 (g1_r3, group `exploit_alpha_EXP_0795`). The Methods must describe this engine and the model search, state that ridge is fixed only in `tools/feature_compare.py` and the package's `evaluate.py`, correct the control's description, and report the engine's share and the selected model's family per lab run; the A2 arm should keep the engine on, as A1 had it, and the plan should say so.

**What the second reader checked:** Confirmed in the files. Every cited line reads as the finding says: the engine is on by default (default.toml:43) and at baa7dfd, runs at most every 15 s whenever queued < workers (controller.py:194-199), proposes add/drop/alpha/model-swap/subset candidates (exploit.py:90-117, 167-171), the planner's JSON may name lasso, elastic net or OLS (prompts.py:37), `best()` ranks across all model types (db.py:203-206), and `--source-run` hands the comparison the top-scored experiment's feature set whatever model chose it (feature_audit.py:1030-1033, feature_compare.py:1136). Neither document mentions the engine or the model search, including the PLAN's dated notes; the A2 script passes no override. Two things strengthen it beyond the finding: (1) the paper's description of C0 as "fixed hypothesis templates" (:133-135) is also incomplete, since 61-95% of a scripted control's experiments are the engine's follow-ups (scaling.md:16, columns 2-4; :40-44); (2) in g1_r3, one of the three A1 runs already in block H's table, the selected model EXP_0796 is itself an engine proposal (hypothesis_group exploit_alpha_EXP_0795), so the engine is not only a share of the search but the author of a reported winner. Two caveats on the finding's own details: the 0.290 ± 0.008 share is from the DeepSeek-planned runs on code 537344f (n=2), not from block G's baa7dfd, whose share no reading records; and the engine's swap loop covers ridge/lasso/elasticnet only (exploit.py:112), OLS comes from the planner, which the finding states correctly. The one part of the proposed fix to reject: running A2 with `--set schedule.python_exploit=false` would be wrong, because A1 is block G's runs, not re-run, with the engine on, and block_h_a2.sh:4 fixes A2 as differing from A1 in the worker count only; switching the engine off would confound the A1/A2 comparison and make A2 unlike C0 too. Severity major, not reject: the fair test does fix ridge (feature_compare.py:1085, evaluate.py:472), the engine is part of the lab system under comparison and C0 shares it, so no reading becomes invalid; but the abstract's framing and the Methods' description of two arms are false as written and must change before submission, and the PLAN should pre-register the engine's setting and the per-run readings before A2 runs.

**Fix:** 1. PAPER abstract :14-15: reword to "with the scoring model fixed to one ridge regression" (or "every system's features scored on one fixed ridge"), since the lab's own search is not model-fixed. 2. PAPER Methods, The lab (:84-90): add that the planner's JSON may name ridge, lasso, elastic net or OLS (`genemila/prompts.py:37`, `ALLOWED_MODELS`), and that the controller also queues deterministic follow-ups without an LLM whenever fewer experiments are queued than workers (`genemila/exploit.py`, `schedule.python_exploit = true`, `exploit_depth = 3`): add or drop a feature, refine alpha, refit the best set with ridge, lasso or elastic net, and, once the first tiers run dry, enumerate feature subsets; the run's best is the highest selection score across all of them (`db.py best()`), and the comparison refits that feature set with ridge (`feature_compare.py:1085, 1136`). State explicitly that only `tools/feature_compare.py` and the package's `evaluate.py` fix ridge. 3. PAPER :133-135, C0: say the control is the scripted templates plus the same deterministic engine, which proposed 61-95% of the scripted controls' experiments on record (`docs/results/scaling.md:16`). 4. PLAN Arms (:24-26) and a dated note: pre-register that `schedule.python_exploit` and `exploit_depth` stay at their defaults in A2 and C0, as in A1 (block_h_a2.sh:50-53 passes no override), so A2 differs from A1 in the worker count only; do not run A2 with `python_exploit=false`. 5. PLAN reading 2 (:219-223) and PAPER Table 1: per lab run (A1, A1-ablation, A2, C0) report from `lab.db` the share of completed experiments with `proposer = 'python:exploit'`, the selected experiment's `model_type`, and whether its `hypothesis_group` starts with `exploit_` (g1_r3's does: `exploit_alpha_EXP_0795`); note that lab arms are system-level comparisons in which this engine is part of the system.

### F05. Lab arms write code with deepseek-flash; the paper says every LLM arm ran on one LLM

**Where:** PAPER 21-22, 92-93, 355-356; PLAN 24, 26; protocol 110-113. **Lenses:** fairness, venue. **Second reader (first pass):** confirmed, severity major.

**In a reviewer's words:** The abstract and the Limitations state that every LLM arm ran on one LLM (deepseek-v4-pro), but the Methods and the run scripts show that the lab arms' features were all written by deepseek-flash workers while the Biomni and Codex arms wrote theirs with deepseek-v4-pro; the code-writing model is therefore confounded with the system under comparison and must be named as such in the abstract, Table 1 and the limitations, with the reason the lab keeps the cheaper workers.

**What the second reader checked:** Confirmed in every particular. The lab arms (A1 and A1-ablation from block G, A2 in block H) plan with deepseek-v4-pro and have every feature written by deepseek-flash workers (block_g_run.sh:78-79, block_h_a2.sh:50-51); the package arms have their code written by deepseek-v4-pro (block_h_a3.sh:13, block_h_a4.sh:14). The PAPER's Methods (92-93, 316) say so, but its abstract (21) and Limitations (356) say every LLM arm ran on one LLM, and Table 1's arm labels carry no model, so the paper contradicts itself and the lab-vs-package comparison confounds the system with the code-writing model. The protocol's fairness control 3 ("the same LLM wherever the system allows it", :113) is not met by the lab: run_research.py takes --worker-model and the pricing table holds deepseek-v4-pro, so the lab allows it; the flash workers are an inheritance from B2's settings and a cost choice. The PLAN discloses the fact in its Arms table (24, 26) but gives it no note as a difference, while the far smaller A3 alias fallback gets one (162-164). The direction of the confound is not obvious (a weaker, cheaper code writer, but four of them, more attempts per dollar under the $1.00 worker cap, and a stronger planner), which is exactly why it has to be named. Not touched by PR #70. One correction to the finding's proposed fix (a): running A2 with v4-pro workers would break A2's one stated purpose, to differ from A1 in the worker count only (block_h_a2.sh:4), since A1 is block G's flash-worker runs and is not re-run; fix (b) is the right one, with an optional extra disclosed arm if Andres funds it.

**Fix:** Keep A2 as planned (flash workers, matching A1) and fix the words, before the chain for the plan and before submission for the paper. (1) PAPER 21-22: "The four LLM arms ran three 20-minute sessions each on DeepSeek models: the lab arms plan with deepseek-v4-pro and write every feature with deepseek-flash workers, the package arms plan and write with deepseek-v4-pro". (2) PAPER 356: replace "one LLM, `deepseek-v4-pro`, unless ..." with "one model family; the code-writing model differs between the lab arms (deepseek-flash workers, inherited from B2's settings and kept so A2 matches block G's A1, at about a quarter of v4-pro's price) and the package arms (deepseek-v4-pro), so the system and the code-writing model are confounded in the lab-versus-package reading; the client and isolation differences are likewise disclosed, not removed". (3) PAPER Table 1 (254-258): label the lab rows with their models the way `tools/results_table.py`'s `run_arm` already does ("deepseek-v4-pro planner, deepseek-flash workers") and the package rows "deepseek-v4-pro". (4) PLAN: a dated note before the chain under the Arms table stating that the lab arms' workers are deepseek-flash, why A2 keeps them (it must differ from A1 in the worker count only), and that the reading in section Readings item 2 reports the served model per arm, so the lab rows show two models. (5) Protocol control 3 (:113): "The same LLM (deepseek-v4-pro) for every package arm and for the lab's planner; the lab's workers are deepseek-flash (B2's settings, kept so A1 and A2 match), a disclosed difference." (6) Optional, only on Andres's written approval and as its own arm, never in place of A2: A2-pro, the one-worker lab with --worker-model deepseek-v4-pro under the same $1.00/$1.50 caps, which would separate the code-writing model from the system; note that v4-pro workers get fewer attempts under the same worker cap, so even that arm is matched on money, not on attempts.

### F19. C2 was translated after the lab's Adamson results; two plugins are response-transfer features

**Where:** PAPER 136-138; PLAN 30. **Lenses:** fairness. **Second reader (second reader, 05:05 UTC):** confirmed, severity major.

**In a reviewer's words:** The "CellForge ideas, translated by us" set was written on 16 October 2026 by the same session that, 24 minutes earlier, recorded that the agents' whole gain was transfer of training responses between perturbations sharing gene sets or protein-interaction neighbours, and two of its three Adamson-scoreable plugins (cf_pathway_transfer, cf_latent_offset) are exactly those two transfers; neither the C2 README nor the paper discloses the date or that knowledge, although the README already discloses it for the analogous hand-written transfer feature ("written after the agent runs had shown what works"). Add the provenance and label the Table 1 row accordingly before any reading of the arm is reported.

**What the second reader checked:** Every factual element checks out and the record is stronger than the finding states. The C2 set was committed at 01:51 UTC on 16 October by the #41 session, 24 minutes after that same session committed README.md:104-105 saying the agents' whole gain was "transfer of the measured responses of training knockdowns whose targets share gene sets or protein-interaction neighbours"; cf_pathway_transfer (leave-one-out mean of training changes of perturbations sharing gene sets) and cf_latent_offset (leave-one-out transfer of training codes through PPI neighbours) are those two mechanisms, one each. The scaling report (4-5 Oct), the hand-written transfer control (5 Oct), the transfer ceilings (11 Oct) and B1/B2 (11-12 Oct) all predate it. The protocol's own 15 October wording was "pathway membership" and "perturbation-embedding similarity"; the implementation turned both into train_delta-reading transfers, which is the free translation choice the finding describes. Neither the C2 README's Provenance section (CellForge file:line citations only), PAPER 136-138, Table 1 (262) nor the paper's own "three changes belong in the paper" disclosure paragraph (228-241) says when C2 was written or what its author had seen, and the PLAN's dated notes never mention C2. The repository already applies the disclosure the finding asks for to the analogous object (README 477-478, 488-490: the hand-written transfer feature "written after the agent runs had shown what works"), so the omission for C2 is an inconsistency with the project's own standard, not a new demand. Mitigations that keep this from "reject": the paper does say C2 is hand-written with no session, no arm claim is made from the development tier, and the fix is an additive disclosure that invalidates no number.
