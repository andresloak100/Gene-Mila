# What the agents were told: prompts, starting features, control and worker settings

Every quoted block below is copied from the code by a script at commit 8261c57 (the file is generated from
`genemila/prompts.py`, `genemila/features/builtin.py`, `genemila/providers/mock.py`, `genemila/controller.py` and
`configs/default.toml`, so the text is byte-identical to what the runs used). The prompts have not changed since
commit 7787cb7, which is before the first run in the results table, so every arm in docs/results received the same
planner and worker prompts; what differs between arms is the planner model, the worker count, the selection code
and, for the control, that no LLM is called at all.

## 1. The loop in one paragraph

A run is one dataset, one split, one time budget (20 minutes in every run reported) and `workers` worker slots. The
Python controller first runs five baselines (section 4). Then, whenever fewer experiments are queued than twice the
number of workers, it builds the compressed research state (section 3) from the experiment database and sends it to
the planner (Claude Opus through the Claude CLI, or DeepSeek V4 Pro, or the scripted list of section 5) asking for a
batch of hypotheses as JSON. Each hypothesis becomes one queued experiment: one new feature, one combination or
ablation, or one parameter sweep (sweeps and combinations are generated by Python, no LLM). A worker slot takes the
next queued experiment, creates its own git worktree, and, for a new feature, sends one request to the worker model
(DeepSeek `deepseek-flash`) with the prompt of section 2b; the returned Python file is smoke-tested and guard-checked
(no file, network or OS access, no reading of labels outside the leave-one-out rule), retried once with the error if it
fails, then the controller fits ridge regression over the alpha grid on the feature set, scores it on the visible
perturbations, records everything (hypothesis, parent, files changed, seed, CPU seconds, RAM, metrics, delta from
parent, failure reason, commit hash) and frees the slot. At the deadline the controller stops everything, takes the
three experiments with the best visible selection score, and scores them once on the sealed query-only
perturbations; that sealed score of the finalist with the best visible score is the held-out number in the tables.

## 2. The prompts, verbatim

```text

The lab predicts post-perturbation gene expression (pseudobulk of perturbed cells, unpaired with controls)

Scientific progress must come from FEATURES of (p, g): biologically or statistically motivated signals.

- Each experiment tests ONE clear idea (one new feature, or one combination/ablation, or one sweep).

- Features may use training labels only leave-one-out (excluding the row's own perturbation).
- Parameter sweeps are run by Python without LLM workers: use action "sweep" for them.

Respond with a single JSON object and nothing else.
```

## 3. The research state the planner reads

Python builds it from the SQLite experiment database before every planner round (`genemila/research_state.py`). Its
sections, in order: DATASET, PRIMARY METRIC, KNOWLEDGE AVAILABLE, BASELINES, CURRENT BEST (score, features,
model, alpha, coefficients, the five worst and three best perturbations, error by control-expression quartile, the
ratio of predicted to true change size), FEATURE REGISTRY, FEATURES THAT HELP, FEATURES THAT DO NOT HELP,
HELPFUL FEATURES MISSING FROM BEST, POSSIBLE INTERACTIONS UNTESTED, FAILED DIRECTIONS, UNEXPLORED IDEA AREAS,
IN FLIGHT, RECENT EXPERIMENTS, COMPUTE. The planner never sees raw data, code, or the sealed labels.

The DATASET line is built as
`<name>: <n_genes> genes, <n_control_cells> control cells, <n_train> training perturbations (single-gene targets); predict unseen perturbations.`
For the Adamson runs that is 2,055 genes and 50 training perturbations (the 17 visible validation perturbations are
scored, not trained on; the 21 query-only perturbations are never mentioned). The KNOWLEDGE AVAILABLE line lists
the Adamson bundle's prior-knowledge files: `gene_sets` (pathway and module gene sets), `ppi_network`
(protein-protein interaction edges), `prior_network` (signed regulator-to-target edges), `targets` (which gene each
perturbation knocks down) and `transcription_factors`.

## 4. The starting model and the built-in features

Every run starts with the same three features, defined in `genemila/features/builtin.py`:

```python
"""Baseline features. Agents add new ones in genemila/features/plugins/."""

from __future__ import annotations

import numpy as np

from .api import Feature, FeatureContext, register


@register
class ControlMean(Feature):
    name = "control_mean"
    description = "Mean expression of gene g in control cells."
    rationale = "Highly expressed genes have more room to change; captures scale effects."
    inputs = ["control_cells"]

    def compute(self, ctx: FeatureContext, perts, params):
        return np.broadcast_to(ctx.control_mean[None, :, None], (len(perts), ctx.n_genes, 1)).copy()


@register
class MeanResponse(Feature):
    name = "mean_response"
    description = "Average delta of gene g across training perturbations, leaving p out."
    rationale = "Many perturbations share a generic stress/response program."
    inputs = ["train_delta"]

    def compute(self, ctx: FeatureContext, perts, params):
        out = np.zeros((len(perts), ctx.n_genes, 1))
        for i, p in enumerate(perts):
            _, d = ctx.train_delta(exclude=p)
            out[i, :, 0] = d.mean(axis=0)
        return out


@register
class IsTarget(Feature):
    name = "is_target"
    description = "1 if gene g is the gene targeted by perturbation p, else 0."
    rationale = "A knockout directly lowers its own target's expression."
    inputs = ["targets"]

    def compute(self, ctx: FeatureContext, perts, params):
        out = np.zeros((len(perts), ctx.n_genes, 1))
        for i, p in enumerate(perts):
            out[i, ctx.target_indices(p), 0] = 1.0
        return out
```

The five baselines run first in every arm, control included:

1. EXP_0001, "predict no change": every perturbation predicts the control mean (pearson_delta 0 by construction).
2. EXP_0002, mean training response: every perturbation gets the average training delta.
3. EXP_0003, OLS on the three built-in features.
4. EXP_0004, ridge on the three built-in features (alpha chosen on the visible score from the grid).
5. EXP_0005, lasso on the three built-in features.

"Gene-Mila starting model (OLS, 3 built-in features)" in the results table is baseline 3, the best of the five on
this data (0.520 sealed pearson_delta). Everything above that line in a run is a feature an agent wrote, a
combination of such features, or a penalty or model-family change around them.

## 5. The no-LLM control

The control is the same controller, same baselines, same worker pipeline, same time budget, same selection, with
two substitutions: the planner is `ScriptedPlanner`, which returns a fixed list of hypotheses in a fixed order, and
the worker is `MockProvider`, which answers each hypothesis with a fixed, hand-written plugin file chosen by keywords
in the hypothesis text (so the "implementation" of each idea is the same every time; six control runs gave identical
scores). No LLM is called anywhere in a control run; it costs nothing and is deterministic.

The scripted hypothesis list (`SCRIPTED_HYPOTHESES` in `genemila/providers/mock.py`). The fourteen control runs in
the results table used the first seven; the eighth, `response_components`, was added at commit 74e07ca for the
single new-feature control run and is the hand-written transfer feature described in the collaborator summary:

1. **Target co-expression** (`coexpr_target`, category explore). Hypothesis sent to the worker: "Adding Pearson correlation in control cells between the target gene and gene g improves prediction of unseen perturbations." Rationale: "Genes co-expressed with the knocked-out gene share its regulatory program and should move with it."
2. **Prior regulatory network** (`prior_network_edge`, category explore). Hypothesis sent to the worker: "Adding signed prior-network edge from the target to g, scaled by target expression improves prediction of unseen perturbations." Rationale: "Knocking out a TF removes its regulation of known targets."
3. **Pathway membership** (`shared_module`, category explore). Hypothesis sent to the worker: "Adding gene-set co-membership of target and g (module/pathway) improves prediction of unseen perturbations." Rationale: "Knockouts disturb the pathway they belong to."
4. **Similar perturbation transfer** (`similar_pert_knn`, category explore). Hypothesis sent to the worker: "Adding kNN transfer: average response of training perturbations with similar (co-expressed) targets improves prediction of unseen perturbations." Rationale: "Perturbations of functionally related genes have similar responses."
5. **Target knockdown magnitude** (`target_level`, category exploit). Hypothesis sent to the worker: "Adding control mean of g if g is the target (target expression level) improves prediction of unseen perturbations." Rationale: "The knockdown drop scales with the target's baseline expression."
6. **Latent program alignment** (`pca_alignment`, category risky). Hypothesis sent to the worker: "Adding PCA loadings product of target and gene g on top PCs improves prediction of unseen perturbations." Rationale: "Shared latent programs predict co-movement."
7. **Gene variability** (`control_variance`, category explore). Hypothesis sent to the worker: "Adding control-cell std of gene g (variance) improves prediction of unseen perturbations." Rationale: "Variable genes respond more."
8. **Response components** (`response_components`, category explore). Hypothesis sent to the worker: "Adding low-rank response components of the training perturbations, with p's weight on each predicted from its target's annotations by kernel ridge improves prediction of unseen perturbations." Rationale: "A few shared programs make up most responses; mapping a target's annotations to the programs' weights extrapolates to targets without a close training perturbation."

Once the list is exhausted the scripted planner proposes, in order: adding to the current best model each feature
that helped on its own but is missing from it (one per round, greedily); one ridge-penalty sweep over
[0.001, 0.01] and [300, 1000, 3000]; one lasso fit on the best feature set. After that it proposes nothing, and the
run continues on the Python exploit engine alone (section 6), which is why a control run exhausts its ideas in two
to three minutes.

The mock worker's fixed implementations, keyed by words in the hypothesis text (first match wins; `variance` is the
fallback):

| template | chosen when the hypothesis text contains |
|---|---|
| `external_knn` | external screen neighbour (added after commit 8261c57, see below) |
| `external_direct` | external screen response (added after commit 8261c57, see below) |
| `components` | component, low-rank, low rank, kernel ridge |
| `similar` | similar, knn, neighbor, neighbour, transfer |
| `network` | network, prior, edge, regulat, tf |
| `module` | module, pathway, gene_set, gene set |
| `pca` | pca, principal, latent, svd |
| `coexpr` | coexpr, co-expr, correlat |
| `target_level` | target_level, knockdown, self, target expression |
| `variance` | varian, dispersion, std |

The template code is in `TEMPLATES` in the same file (control-cell co-expression with the target, signed prior-network
edges, gene-set co-membership, kNN response transfer by target similarity, target expression level, PCA loading
products, control-cell variance, and the low-rank response components with kernel ridge).

Added on 2026-10-11, after every run above: when a run can read an external screen knowledge file added to its bundle
after the build (run.external_knowledge, for example knowledge/replogle2022_k562.json built by
tools/build_external_screen.py), `ScriptedPlanner` appends two hypotheses per such file after the eight above,
`external_direct_<file>` ("external screen response of the same target gene, from knowledge file <file>") and
`external_knn_<file>` ("external screen neighbour transfer: training responses weighted by how alike their targets'
knockdowns look in knowledge file <file>"). Their templates read the file named in the hypothesis: the first one
copies the screen's change for the same target gene (0 where unmeasured or without a row); the second averages the
other training perturbations' changes weighted by the correlation of their targets' external changes with the
target's (top 5 positive; the mean training change otherwise). A bundle without such a file gets the unchanged list,
and a run with one is its own arm, "scripted control (no LLM) (external knowledge: <file>)".

## 6. What a worker is, and what the worker count changes

A worker is not a persistent chatting agent. It is an asynchronous slot in the Python controller that runs the
pipeline of section 1 for one experiment at a time: claim the next queued experiment, make a git worktree, call the
worker model once (plus at most one repair call) if the experiment needs a new feature, run the guards, run the CPU
experiment, score, record, release. The LLM is active only during the implement and repair calls; while features
compute and ridge fits run, no tokens are spent. Combinations, ablations and sweeps need no LLM call at all.

`run.workers` (1, 4, 8, 16 in the comparison) is the number of such slots, so it is the number of experiments in
flight at once. It also sets, through the defaults in `configs/default.toml`:

| setting | rule | 1 worker | 4 workers | 8 workers | 16 workers |
|---|---|---|---|---|---|
| hypotheses per planner round (`planner_batch`) | 2 x workers, clipped to 6..12 | 6 | 8 | 12 | 12 |
| planner rounds allowed at once (`planner_concurrency`), each with its own focus (section 2a) | ceil(workers / 6) | 1 | 1 | 2 | 3 |
| planner is asked again when fewer than this are queued (`queue_low_water`) | 2 x workers | 2 | 8 | 16 | 32 |
| Python exploit engine fills the queue when fewer than this are queued | workers | 1 | 4 | 8 | 16 |
| planner usage cap per run | $4 x max(4, workers) x hours | $5.3 | $5.3 | $10.7 | $21.3 |

So more workers means more experiments per minute, larger and more frequent planner rounds (the planner is asked
for more ideas, and in parallel with different emphases), and a proportionally larger share of experiments
generated by the deterministic exploit engine whenever the planner cannot keep the queue full. The exploit engine
(`genemila/exploit.py`) proposes follow-ups around the current best model: add a helpful feature it lacks, add the two
best missing ones together, drop one of its features, refine the ridge penalty around the chosen alpha, swap the
model family; when those are exhausted it widens to every known feature and the next-best parents, then to small
feature subsets. Every candidate is hashed and never proposed twice, so the engine runs dry rather than looping.
The worker model, the per-experiment caps (300 s timeout, 4 GB RAM, one new feature per experiment) and the
scoring are identical at every worker count.

Mix of hypothesis categories asked of the planner in every run: 65% explore (new features), 25% exploit (refine or
combine what works), 10% risky; the scheduler also raises the priority of queued experiments whose category is
under-represented. The planner may ask for up to 3 replicates of one hypothesis, sent to independent workers for
different implementations.

## 7. Settings of the reported runs

All runs: Adamson 2016 (CRISPRi, K562), CellForge's seed-42 split (50 train, 17 visible validation, 21 query-only),
2,055 genes, 20-minute budget, ridge by default with alpha grid [0.01, 0.1, 1, 10, 100] (the planner may also ask
for lasso, elastic net or OLS, and sweeps widen the grid), one new feature per experiment, five baselines first,
three finalists plus their average scored once on the sealed set at the end.

- Worker-count comparison (`scale_w{1,4,8,16}_r{0,1}`, code 2492e11): Opus planner through the Claude CLI,
  `deepseek-flash` workers, selection on the 17 visible validation perturbations only, seed 1 for the second repeat.
- Planner check and later 4-worker runs (code 537344f and after): the same, except that selection is cross-validated
  over all 67 visible perturbations (`cv_folds = 5`), and `newcode_ds_w4_r*` used DeepSeek V4 Pro as the planner
  instead of Opus; `newcode_derule_opus_w4_r0` used the selection rule `pearson_delta+r2_top`.
- Controls (`control_*`): scripted planner and mock worker as in section 5, otherwise the same settings as the arm
  they are placed against; the warm-started run `control_components_from_opus_r0` began from the finished state of
  `newcode_opus_w4_r0` instead of from the baselines.

The exact command lines of the paid runs are in `tools/scale_seq.sh`; every run's full configuration is saved in
its run directory as `config.json`, and the per-round planner inputs and outputs in its `artifacts/` directory.
